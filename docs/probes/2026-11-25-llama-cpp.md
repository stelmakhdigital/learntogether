### Обрыв по бюджету (`raw/probe5_raw.txt`, `max_tokens: 20`)

```

"usage":{"completion_tokens":20,"prompt_tokens":208,"total_tokens":228,
"prompt_tokens_details":{"cached_tokens":207}}
```

Накопленные аргументы: `{"statement": "вектор — это` (обрывок кончается ровно здесь, пробела в конце нет) — непарсящийся JSON, не пустой.
То есть обрыв надо отличать от «модель не вызвала инструмент» именно по факту
пришедших дельт.

### Параллельные вызовы (`raw/probe6_raw.txt`, 51 чанк)

Без флага `--parallel` сервер вернул два вызова с `index: 0` и `index: 1`, у каждого
свой `id` и `name` в первом чанке своего индекса:

```
0 record_step {"statement": "вектор — это стрелка с длиной", "kind": "foundation"}
1 record_step {"statement": "из этого следует что у вектора есть направление", "kind": "derivation"}
```

Значит «сервер не отдаёт параллельные вызовы по умолчанию» для этой сборки неверно:
отдаёт, и протокол обязан выдерживать несколько индексов, даже если сам их не просит.

### Без `--jinja` (`raw/probe7_raw.txt`)

Отличий от пробы с `--jinja` нет: вызов вернулся вызовом, `finish_reason:
"tool_calls"`, 23 дельты аргументов, `content` пустой. Сервер подставил шаблон из
самого GGUF (`chat_template` в `/props` присутствует в обоих случаях). Утверждение
`docs/local-servers.md`, что без `--jinja` вызовы не работают, на этой сборке и модели
не подтвердилось; флаг решает только загрузку внешнего шаблона.

### Точный счёт токенов

Цепочка, которая воспроизводит счёт сервера бит в бит:

1. `POST /apply-template` с `{messages, tools, add_generation_prompt: true}` →
   отрендеренный промпт (894 символа, начинается с `system\n...`);
2. `POST /tokenize` с `{content: <промпт>, add_special: false}` →
   `{"tokens":[...]}`, ровно 214 элементов, отдельного поля-счётчика нет;
3. `POST /v1/chat/completions` с теми же сообщениями и `max_tokens: 1` →
   `usage.prompt_tokens = 214`.

Расхождение 0 токенов (0.00%). Файл `tokenizer.json` для этого сервера не нужен.
`/tokenize` шаблон не применяет — если подать в него сырое сообщение вместо
отрендеренного промпта, число не совпадёт.

### Логи

При `verbosity = 3` (дефолт) строк про чат-шаблон, tool-парсер или Jinja в логе нет
(проверено на обоих сохранённых логах и на полном логе пробы 8). Способ узнать
поддержку вызовов — `chat_template_caps`, а не разбор лога.

## Итог по правилам транспорта

| Правило | Итог | Факт |
| --- | --- | --- |
| 1. накопление по `tool_call.index`, пустые дельты и `finish_reason: null` до последнего — норма | подтверждается | `index: 0` в каждой дельте, `finish_reason: null` до предпоследнего чанка, аргументы в 23 дельтах |
| 2. вызов определяется по наличию `tool_call`, а не по `finish_reason` | подтверждается | в пробе 5 дельты вызова шли при `finish_reason: "length"` |
| 3. `length` или непарсящийся JSON — вызов мёртв, обрывок не дочитываем | подтверждается, ситуация воспроизведена | накоплено `{"statement": "вектор — это` |
| 4. `tool_choice` не отправляем | не проверено | запросов с `tool_choice` не было |
| 5. reasoning включаем только при подтверждённой пробе | подтверждается для этой модели: выключен | `reasoning_content` не приходил ни в одном чанке; на рассуждающей модели не проверялось |

Отдельно: `prompt_tokens_details.cached_tokens` = 207 из 208 на повторном запросе —
кэш промпта сервер сообщает, и это поле идёт в `Usage.inputCacheRead`.

## Что осталось непроверенным

- `tool_choice` (правило 4) и поведение при `none`/`required`.
- Модель с reasoning: приход `reasoning_content` и цена его повторной отправки.
- Эмбеддинги и `bge-m3` — другая сборка/инстанс, пробы не делались.
- Две другие модели (разные tool-парсеры) и Anthropic/Ollama — только по плану на этапе 2.
- Прогон на 24 ГБ+ (релизный таргет): здесь контекст был 6144 из-за 6 ГБ карты.
