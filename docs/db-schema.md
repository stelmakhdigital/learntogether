# Схема хранилища

SQLite — единственный источник правды (D-002). Читаемые файлы (Markdown на сессию,
JSONL на граф) — детерминированный экспорт, а не хранилище. Файл схемы:
`packages/data/migrations/001_init.sql`. Ниже — почему именно так, а не описание
полей.

## Проверено на живом SQLite

Прогон на этой машине (better-sqlite3 13.2.0, Node 24.22.3): схема создаётся
целиком, 35 полезных таблиц плюс теневые таблицы FTS5; FTS-триггеры корректно
переживают UPDATE утверждения — старая формулировка после правки не находится,
новая находится; внешний ключ на несуществующую сессию отбит; `why_needed NOT NULL`
отбит; удаление сессии каскадом чистит транскрипт и следы.

## Группы таблиц

- История: `session`, `transcript_entry`, `tool_call`, `repair`, `coverage`.
- Метод: `goal`, `probe_item`, `plan`, `plan_node`, `step`, `step_check`.
- Граф: `claim`, `claim_alias`, `chain`, `chain_premise`, `provenance`, `doubt`,
  `claim_embedding`.
- Практика: `repeat_item`, `attempt`.
- Источники: `source`, `source_chunk`.
- Модели: `endpoint`, `model_info`, `role_assignment`.
- Служебные: `migration`, `job`, `event`.

## Решения внутри схемы

Транскрипт построчный. `transcript_entry` — строка на часть хода с `ordinal`
внутри сессии и `UNIQUE (session_id, ordinal)`. Одна JSON-запись на сессию
означала бы переписывание всей истории на каждый ход и раздувание её картинками
(D-020). Вложения в БД не хранятся: файл по content-hash, в базе ссылка.

`step_check`, а не `check`: `CHECK` является ключевым словом SQL, имя пришлось
сменить. Ограничений на «одна проверка на шаг» в схеме нет — отремонтированный шаг
получает вторую проверку. Обязательство метода («нет принятия без проверки»)
держится прикладным слоем и тестом, а не триггером: триггер не различает
`verdict` момент, когда шаг приняли.

Внешние ключи по умолчанию `RESTRICT`. Удалять узел графа, молча стирая уроки,
которые на него опираются, хуже громкого отказа. Каскад оставлен там, где дочерние
строки не имеют смысла без родителя: транскрипт и правки аргументов.

`model_info.context_tokens` допускает `NULL`, и это осмысленное значение: «не
измерено». Числа по умолчанию в схеме нет намеренно — тихая подмена неизвестного
константой и есть тот провал, с которого начали (D-006).

`repair` обязана хранить каждую правку аргумента вызова. Правка без записи
запрещена контрактом: иначе невозможно доказать, что эталонный ответ ученику не
подменяли после генерации.

`claim_fts` и `transcript_fts` — FTS5 с триггерами и `unicode61
remove_diacritics 2` (поиск по русскому без учёта ё). Векторы лежат отдельной
таблицей `claim_embedding` и перебираются brute-force: расширение для векторов не
берём (D-004, D-039), а гибрид с BM25 обязателен (D-040).

`doubt` — частичный индекс по открытым зонам сомнения: практика начинается с них,
и искать их полным сканом на каждом открытии экрана незачем.

`event` — кольцевой буфер диагностики. Ограничение по количеству строк держит
приложение, индекс по `created_at` делает обрезку дешёвой. Приватное содержимое из
него исключается при экспорте, а не при записи: иначе отладка невозможна.

## Миграции

Файлы `NNN_name.sql` применяются по имени в транзакции, каждая записывается в
`migration(name, applied_at)` вместе с чек-суммой содержимого. Изменение уже
применённого файла — ошибка с именем файла, а не «переприменим». Так держится
инвариант: один и тот же файл схемы даёт одну и ту же базу на любой машине.

## Что здесь ещё не решено

- Полнотекстовый поиск по утверждениям ищет точные формы; морфология русского
  (окончания) даёт пропуски. Кандидат — легковесный стеммер на уровне приложения,
  решение примем на этапе 4 вместе с корпусом проверки.
- Конфликты слияния (несколько устройств) не рассматриваются: синхронизации в v1
  нет (U-005). Таблицы спроектированы так, чтобы слияние было возможно: идентификаторы
  текстовые, порядок — производный от `ordinal` и времени.
