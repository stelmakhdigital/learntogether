# Архитектура

Документ этапа 0. Пункты с `TODO(scout-*)` закрываются фактами из проверки и не
уходят в реализацию открытыми.

## Цели, которые диктуют архитектуру

1. Работа полностью с локальной моделью; внешний провайдер не может быть точкой
   отказа ни одной функции.
2. Неизвестное о модели не подменяется константой: либо измерено, либо спросено.
3. Ни одного хода обучения без проверки; ни одной опоры на непроверенное.
4. Данные пользователя читаемы и переносимы, но не ценой линейного роста стоимости
   чтения.
5. Код извне (расширения) не получает прав на файлы, сеть и ключи по умолчанию.

## Пакеты и направления зависимостей

```
packages/domain    модель предметной области и правила. Без I/O, без сети, без UI
packages/data      схема БД, миграции, репозитории, экспорт в читаемые файлы
packages/models    адаптеры провайдеров, пробирование, бюджеты, репарация вызовов
packages/agent     цикл агента, инструменты, состояния хода. Чистый по вводу/выводу
packages/server    HTTP + SSE, задания, доступ, сборка контекста, хранение
apps/ui            интерфейс и состояния
apps/desktop       Electron-шелл
apps/cli           read-only доступ к данным для внешнего анализа
```

Разрешены только стрелки вниз. `agent` не импортирует `data` и `server`: цикл
получает контекст аргументами и отдаёт события, персистентность делает `server`.
`cli` и `server` используют `data` независимо друг от друга — поэтому репозитории
живут не в `server`. Отличие от первоначального списка пакетов в `AGENTS.md`
зафиксировано как решение D-019.

## Доменная модель

Ключевое различие: сессия (что происходило) и граф (что стало знанием). Граф не
хранит оценок усвоения; усвоение живёт в проверках, зонах сомнения и очереди
повторений.

Сущности:

- `Goal` — цель. Сырая формулировка + уточнённое состояние цели, собранное при
  замере. Живёт дольше сессии.
- `Session` — сессия обучения или практики. Хранит профиль моделей на момент хода.
- `ProbeItem` — результат зондирования: утверждение, состояние `held | frontier |
  absent`, заявленная уверенность, ссылка на ответ-основание.
- `Plan` и `PlanNode` — дерево зависимостей от границы держания к цели. Узел: формулировка,
  позиция, обоснование, статус. Узел плана — landmark, а не абзац урока.
- `Step` — один шаг рассуждения. Тип `derivation | foundation`, формулировка факта,
  опоры (предпосылки), статус `presented | checked | repaired | accepted`.
- `Check` — проверка шага. Тип, вопрос, варианты, эталон, ответ ученика, вердикт,
  заявленная уверенность, время ответа.
- `Claim` — узел графа: утверждение, область, теги, формулировки-варианты, провенанс
  на шаг/сессию/источник.
- `Chain` — `premises[] -> conclusion`, провенанс. Совместная достаточность, не
  независимые стрелки.
- `Doubt` — зона сомнения: узел, источник (провал проверки, противоречие), статус,
  последний ремонт. Из неё строится практика в первую очередь.
- `RepeatItem` — элемент повторения: узел, метод `recall | reasoning | transfer`,
  состояние планировщика, источник.
- `Attempt` — попытка практики: элемент, ответ, вердикт, оценка планировщику.
- `Source` и `SourceChunk` — импорт (путь, хэш, размер, статус).
- `Endpoint` — профиль эндпоинта: базовый URL, режим ключа, способ доступа. Ключа в
  БД нет.
- `ModelInfo` — модель эндпоинта + измеренные возможности: контекст, вызовы
  инструментов, reasoning, vision, эмбеддинги, способ замера и время пробы.
- `RoleAssignment` — роль (`teacher | probe | background | embed | vision`) к модели.
- `Event` — диагностика: кольцевой буфер, экспорт фильтруется по флагу.

## Поток одного хода

1. Клиент присылает ход: новый запрос, ответ на проверку или результат вызова
   инструмента.
2. `server` собирает контекст: транскрипт после watermark, ровно одно активное
   sammary, узлы плана, выжимку графа, инструкции роли, схемы инструментов.
   Размер считается точно: рендер chat_template и encode промпта (D-022), бюджет —
   из измеренного контекста, не из константы.
3. `agent` делает цикл: вызов модели, разбор вызовов инструментов, внутренние
   инструменты исполняет сервер, вопрос ученику оканчивает ход.
4. Каждый завершённый элемент (сообщение, шаг, проверка, вызов) пишется и уходит в
   SSE сразу, не в конце хода.
5. После хода в очередь встают: обновление покрытия, извлечение в граф, пересчёт
   очереди повторений.

Вопрос ученику — единственный способ получить от него структурированный ответ:
вызов инструмента с валидируемой схемой и завершением хода. Разбор свободного
текста ответа отсутствует намеренно; при битых аргументах вызов повторяется с
конкретной ошибкой.

## Хранилище

Один источник правды — SQLite в WAL, один писатель на процесс. Читаемые файлы
(Markdown на сессию, JSONL на граф) — детерминированный экспорт по требованию, при
закрытии сессии и перед перезапуском.

Таблицы:

```
meta                     версия схемы, watermark компакции, идентификаторы профиля
goal, session, transcript_entry, tool_call
plan, plan_node, step, check, probe_item
claim, claim_alias, chain, chain_premise, provenance, node_position, graph_setting
doubt, repeat_item, attempt, side_thread, side_message
source, source_chunk, coverage
endpoint, model_info, role_assignment
job, event
```

Правила:

- Транскрипт — строки с порядковым номером и типом, не один JSON на сессию. Иначе
  каждое сохранение переписывает всю сессию.
- Вложения (изображения, кадры PDF) — файлы по content-hash, в БД ссылка и метаданные.
- `claim_fts`, `transcript_fts` — FTS5 внешние списки; семантика — вектор в BLOB и
  brute-force сравнение. `проверено`: FTS5 включён в готовую сборку better-sqlite3
  13.2.0, загрузка расширений через `db.loadExtension()` на готовом бинарнике возможна,
  но векторное расширение не подключаем: sqlite-vec не обновлялся с мая 2026.
- Sammary компакции: одна активная строка на сессию + watermark. Старое вытесняется,
  история сообщений не меняется. Инвариант теста: суммарные токены входа по ходам
  не растут.
- Никаких каскадных удалений «в никуда»: удаление узла графа обязано оставить
  следы в проверках и элементах повторения либо явно их открепить. Тест на
  отсутствие висящих ссылок.

## Модельный слой

- Один внутренний формат запроса и ответа; адаптеры на `chat/completions`,
  `messages`, нативный API локального сервера.
- Проба возможностей при подключении, при смене модели и по протухании пробы:
  контекст, вызовы инструментов, reasoning, vision, эмбеддинги, скорость. Результат
  с указанием, чем измерен.
- Неизвестная возможность = вопрос в интерфейсе с предложением измерить. Констант
  вроде «2048 на всякий случай» в коде нет.
- Репарация вызовов инструментов: нормализация дельт, допарсинг частичного JSON,
  повтор с текстом ошибки, честный отказ после N попыток — контракт и наборы
  инструментов в `docs/tool-contracts.md`;
- Профилей эндпоинтов несколько, ключ в хранилище ключей ОС (`@napi-rs/keyring`,
  на Linux хранилище пиним явно; без secret-service ключ остаётся в памяти).
- Бюджет входа считается точно: рендер chat_template и encode итогового промпта
  (`tokenizers-wasm`, `проверено` на Qwen2.5, Qwen3, Llama 3.2), с сверкой по
  `prompt_eval_count` или `usage.prompt_tokens`. Нет токенизатора модели — просим
  файл, временная верхняя оценка не является основанием для компакции.
- Если сервер сам не отдаёт ни шаблон, ни счётчик (vLLM: `/apply-template` — 404),
  размер хода берётся у него же: тот же запрос с `max_tokens: 1` называет
  `usage.prompt_tokens` своего входа, и проба верит этому после сверки с полным
  вызовом (`tokenizer_source = 'usage'`, D-072). Ни одного числа по-char-оценке.

## Интерфейс

- Реестр экранов: каждый обязан объявить EMPTY, LOADING, PARTIAL, ERROR, OFFLINE,
  LONG-CONTENT. Тест обходит реестр и требует покрытые состояния.
- Лента сессии и вопросы с виртуализацией; длинный контент разворачивается, а не
  ломает макет.
- Два канала (D-044): `GET /sessions/:id/stream` отдаёт транскрипт по курсору
  `afterOrdinal` — это возобновимая лента истины; `GET /sessions/:id/turns/live`
  отдаёт ход в реальном времени (текст, мысли, статус вызова, текст отказа) и
  истиной не является: потерянный кадр не теряет данных.
- Доступ вне localhost: обязательный токен и HTTPS, иначе сервер сам поднимает
  самоподписанный сертификат и пишет об этом в логи запуска.

## Расширения

Дочерний процесс, RPC, манифест прав (`question-type`, `problem-type`, `view`,
`practice-source`, файлы, сеть). Без выданной правы вызов не исполняется. Падение
расширения не роняет сервер. Этап 8.

Имя, под которым право запрашивается, уже есть: возможность инструмента (`graph:read`,
`question:pose`, `problem:pose`, `step:write`, `probe:write`, `goal:write`,
`plan:write`). Выдача собирается по виду сессии, и инструмент без названной возможности
до модели не доходит — состав отказывает по имени (`teach/tools.ts`, D-080). То же имя
расширения получит право на свой тип вопроса или свою тип задачи.

## Процессы и упаковка

- Три процесса: Electron-шелл (окно, меню, обновления), сервер агента (fork того же
  Electron-бинаря с `ELECTRON_RUN_AS_NODE=1`), UI внутри окна. Сервер отделён, чтобы
  его падение не уносило окно и чтобы его можно было перезапустить. Fuse `runAsNode`
  не отключаем.
- Рантайм — Node 24.22.3, тот же, на котором собран Electron 45. Отдельного
  системного node в дистрибутиве нет.
- Сборка: Linux AppImage (toolset 1.0.3, иначе FUSE2 не грузится на Ubuntu 24.04+)
  и deb, Windows nsis и portable — оба с Linux-раннера через wine; macOS dmg — только
  на macOS-раннере. Нативный модуль не пересобираем: N-API prebuilds едут внутри
  пакета, electron-builder распаковывает их из asar.
- Обновления: Windows и Linux через update feed на HTTPS с контрольными суммами;
  на macOS автообновление невозможно без кодовой подписи, там показ версии и ссылка.
- CI: pnpm store и кэш Electron-архивов; `node_modules` не кэшируется никогда.

## Поиск по графу

- Лексика — FTS5 BM25, семантика — dense cosine по BLOB-векторам с brute-force
  сравнением, слияние RRF с k=60. Один только dense путь запрещён: на коротких
  фактографических запросах он даёт измеренные провалы.
- Модель эмбеддингов по умолчанию bge-m3, запасная arctic-embed-m-v2.0; сервер
  эмбеддингов отдельный процесс, чат и эмбеддинги в одном инстансе llama.cpp не
  живут.
- Выбор модели и значение k проверяются на собственном корпусе из 200 утверждений
  на этапе 4, до этого цифры считаем заимствованными из карточек моделей.
