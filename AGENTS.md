# AGENTS.md — правила работы в этом репозитории

Проект: learntogether. Локальный тренажёр понимания с графом знаний и отложенными
повторениями. Local-first: вся работа идёт с локальной моделью, внешние провайдеры
опциональны.

Перед началом: прочитать `PROJECT_MEMORY.md` (решения и причины), `roadmap.md`
(этапы и приёмка), `docs/teaching-method.md` (метод), `docs/architecture.md`
(границы и хранилище), `docs/tool-contracts.md` (контракт модели и инструментов).
Новые решения — в PROJECT_MEMORY.md с причиной.

## Самодостаточность продукта

Ни в коде, ни в комментариях, ни в документации, ни в названиях коммитов нет ссылок,
названий и заимствованных формулировок чужих реализаций. Методика и тексты — свои.
Библиотеки общего назначения использовать можно, чужие промпты и доки — нет.

## Язык

- Ответы, планы, статусы, todo, названия коммитов и заголовки секций — русский.
- Комментарии в коде, имена идентификаторов, сообщения об ошибках в рантайме — английский.
- Общепринятые термины (commit, lint, CI, migration) не переводить.

## Команды

```
pnpm install
pnpm verify        # lint + check:layers + typecheck + test, одно и то же в CI
pnpm lint
pnpm check:layers  # запрет обратных зависимостей между пакетами
pnpm typecheck
pnpm test          # node --test, без сети и без живых серверов моделей
pnpm build         # сборка приложений (пока только apps/ui на Vite)
```

Node берётся из `.node-version` (24.22.3, как в Electron). Системный Node 22 занят
самим агентом разработки, для проекта его использовать нельзя: `export
PATH=/home/arka/.local/share/node-24/bin:$PATH`. Тесты на TypeScript запускаются
нативно, сборка перед тестами не нужна.

## Как вести работу

- Перед шагом — короткий план на русском и todo. В todo всегда держать пункты
  «проверка сборки и тестов» и «разрешение на коммит».
- Коммит только по явной команде пользователя. Разрешение на коммит не означает
  разрешения на push.
- После push не считать работу готовой: дождаться CI этого коммита, доложить номер
  прогона и результат. Красный — назвать причину дословно из лога и чинить; новый
  push только после разбора предыдущего красного.
- Отметки в roadmap.md обновлять вместе с коммитом этапа.

## Правила кода

- Один источник правды — SQLite. Читаемые файлы — производный экспорт, а не хранилище.
- Любая неопределённость о возможностях модели или сервера решается пробированием и,
  если пробирование не удалось, явным вопросом пользователю. Тихих фолбэков на «безопасные»
  константы нет: неизвестный размер контекста не подменяется числом.
- Ошибки не глотать. Отказ честный и конкретный, с тем, что пользователь может сделать.
- Состояния EMPTY, LOADING, PARTIAL, ERROR, OFFLINE, LONG-CONTENT обязательны на экране;
  экран без них не принимается.
- Никакого кода «на будущее». Нет запроса — нет flexibility.
- Каждое нестандартное упрощение помечать `shortcut: <ограничение>, <когда менять>`.
- Проверять, а не предполагать. Факт без проверки в комментарии или доке не оставлять.

## Архитектурные границы

- `packages/domain` — модель предметной области и правила. Без I/O, без сети, без UI.
- `packages/data` — схема БД, миграции, репозитории, экспорт в читаемые файлы.
- `packages/models` — адаптеры провайдеров, пробирование, бюджеты, репарация вызовов.
- `packages/agent` — цикл агента, инструменты, состояния хода.
- `packages/server` — HTTP, потоковая передача, задания, доступ, хранение.
- `apps/ui` — интерфейс и состояния.
- `apps/desktop` — Electron-шелл.
- `apps/cli` — read-only доступ к данным для внешнего анализа.

Зависимости направлены вниз по списку. `domain` не импортирует ничего из остального.
`agent` не импортирует `data` и `server`: цикл получает контекст аргументами и отдаёт
события, персистентность делает `server`. `apps/cli` и `packages/server` используют
`data` независимо друг от друга. Нарушение границы чинить переносом, а не исключением
в линтере.

## Тесты

- Тестируем поведение, а не формулировки промптов и документов.
- Реестр экранов и состояния обязателен: каждый экран объявляет EMPTY, LOADING,
  PARTIAL, ERROR, OFFLINE, LONG-CONTENT, обход реестра это проверяет. Оболочки
  состояний живут в `.ts` на `createElement` — `node --test` не понимает JSX.
- Каждый новый контракт модели, вызова инструмента или состояния БД получает
  contract-тест на фикстуре транспорта.
- Инварианты проверять напрямую (например: суммарные токены входа не растут при
  повторной компакции; ни одного шага без проверки).
- Тестовый код не должен превышать по объёму проверяемый без явной причины.
